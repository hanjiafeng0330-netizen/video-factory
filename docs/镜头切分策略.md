# 镜头切分策略

> 对应实现：`app/adapters/media/scene_detect.py`、`app/adapters/media/ffmpeg.py`、
> `app/capabilities/preprocess_video/capability.py`
> 对应测试：`tests/unit/test_shot_list_building.py`、`tests/integration/test_video_pipeline.py`
> 文档用途：审查切分口径、调参、以及在效果不符预期时定位是策略问题还是素材问题

---

## 1. 为什么这件事值得单独写一份文档

镜头边界是后面所有环节的地基：

- 分镜（T5-1）按镜头对齐画面与口播；
- 视频理解（T3-3）按镜头抽帧，抽错帧就等于让模型看错内容；
- 关键帧数量直接决定视觉理解的调用成本。

**切错的代价不对称且难以追溯。** 漏切会让两个镜头被当成一个，成片里表现为「画面
和口播差半拍」；过度切分会让关键帧数量和视觉理解成本放大数倍，并在分镜里产生
一堆几十毫秒的无意义镜头。这两种错都不会在质检阶段报错，而是以「效果不好」的
形式出现，此时几乎不可能追溯回切分阶段。

所以切分策略必须是可审查、可复现、有回归测试守着的，而不是一个凭感觉调的参数。

---

## 2. 边界与非目标

**做**

- 输出**首尾相接、覆盖全片**的镜头时间边界；
- 每个镜头抽一张关键帧。

**不做**

- **不做任何语义判断。**「这一段是钩子还是证明」属于视频理解（设计文档 6.3）。
  混在一起会让「切分错了」和「理解错了」两类问题无法分辨。
- **不做转场类型识别**（硬切／叠化／推拉）。一期不需要，且它会把切分的输出结构
  复杂化。
- **不做语音转写与画面 OCR。** 它们依赖付费外部服务，而预处理的价值是纯本地、
  零费用、可无限重跑（设计文档 3.1 要求「允许从任意中间产物重新执行」）。塞进来
  会让「重跑一次预处理」变成要花钱的事，于是没人敢重跑。它们是消费本环节音轨与
  关键帧产物的独立能力。

---

## 3. 两步流程

```
视频 ──▶ ① 检测切点 (AdaptiveDetector) ──▶ 原始切点列表
                                              │
                                              ▼
      ② 规整边界 (build_shot_list) ──▶ 首尾相接的 ShotList ──▶ 逐镜头抽关键帧
```

两步分开的原因：第一步依赖具体检测库，第二步是与检测器无关的纯逻辑。分开后
第二步可以脱离视频文件单独测试（那些边界情况用真实素材构造既慢又难），且换检测器
时第二步保证产出仍满足同样的不变量。

---

## 4. 第一步：检测切点

### 4.1 算法

**PySceneDetect 的 `AdaptiveDetector`**，比较**当前帧与邻域滚动均值的偏离**，
在 HSV 三通道上做逐像素差异。

关键在于「滚动均值」而不是「相邻帧固定阈值」：运镜、推拉、光线渐变会让相邻帧
持续存在小差异。固定阈值面对这种情况只有两个结果——要么把渐变累积成误切，要么
为了避免误切而把阈值抬高到漏掉真实硬切。滚动均值把渐变吸收掉，突变仍然显著。

### 4.2 选型的实测依据

用两条专门构造的素材横向对比（构造代码见
`tests/integration/test_video_pipeline.py` 的两个 fixture）：

- **纯色相硬切**：绿 `#007f00` → 深蓝 `#000080`。两者饱和度与明度相同，只有色相
  不同。真实场景对应：同曝光下不同颜色的产品镜头切换、调色序列内部的切换。
- **单一连续运动镜头**：持续旋转 + 色相漂移，**没有任何切换**。真实场景对应：
  手持运镜、转场推拉、灯光变化。

| 方案 | 纯色相硬切 | 运动素材误切 | 结论 |
|---|---|---|---|
| ffmpeg `select='gt(scene,t)'`，任意阈值 | ✗ 完全检不出 | — | 只比较**亮度平面**，色相变化不可见 |
| `ContentDetector` 阈值 27（库默认） | ✗ 漏切 | ✓ 0 处 | 得分 (60+0+0)/3 = 20 < 27 |
| `ContentDetector` 阈值 15 | ✓ | ✗ 4 处 | 为检出色相切换而误切运动素材 |
| **`AdaptiveDetector`（默认）** | **✓** | **✓ 0 处** | **两者兼顾，且不需手调阈值** |

结论：**固定阈值本身是死路**，只能在漏切与误切之间二选一。

### 4.3 灵敏度参数

领域层暴露的是 `shot_sensitivity`，取值 `0.05 ~ 0.95`，**越大切得越碎**，默认 `0.5`。

它被映射到检测库阈值：区间 `(1.0, 5.0)`，线性反向，因此 `0.5 → 3.0`，恰好是
库的默认值。

两条刻意的设计决定：

1. **对外用「灵敏度」而不是「阈值」命名。** 不同检测库的阈值方向相反（有的越大
   越敏感，有的越小越敏感）。暴露阈值必然被传错方向，而传错方向的症状是「镜头数
   不对」——很容易被当成视频本身的特性，而不是参数问题。
2. **默认值必须落在已实测可用的点上，而不是区间上的任意位置。** 这条有测试锁死
   （`test_default_sensitivity_hits_the_library_default`）。原因见第 7 节的变更记录：
   第一版正是因为没遵守这条而漏切。

映射逻辑收在适配器里，所以换检测器时业务侧参数语义不变。

## 5. 第二步：规整边界

`build_shot_list(cut_points_ms, duration_ms)`。四条规则，每条对应一个实际遇到的
问题：

| 规则 | 具体行为 | 理由 |
|---|---|---|
| 丢弃越界切点 | `≤0` 或 `≥ duration_ms` 的切点忽略 | 检测器偶尔吐出边界外的点 |
| 合并过近切点 | 与上一个边界间隔 `< 400ms` 的切点丢弃 | 快剪闪切会连续吐出好几个相邻切点，那些「镜头」抽出的帧没有分析价值，还把帧数放大数倍 |
| 末尾残片并回 | 最后一段不足 `400ms` 时并入上一镜头 | 否则留一个几十毫秒的镜头 |
| **强制首尾相接** | 镜头序号连续，`shot[i].start == shot[i-1].end`，首镜头从 0 开始，末镜头到全片结束 | 空隙或重叠会让下游分镜对齐出现**无法定位**的偏移 |

最小镜头长度常量：`_MIN_SHOT_MS = 400`（`app/adapters/media/ffmpeg.py`）。

**检测不到任何切换时返回一个覆盖全片的镜头，不是空列表。** 空列表会让所有下游
代码到处判空。

首尾相接这条不只是后处理，还是 `ShotList` 模型的校验器（`app/domain/media.py`），
构造不合法的镜头列表会直接抛错——任何新检测器都无法绕过。

## 6. 关键帧策略

**每个镜头均匀抽 N 帧**，默认 N=3。这样视频理解能看到镜头内的动作起止，而不是只看到
中间那一瞬。

| 项 | 取值 | 理由 |
|---|---|---|
| 每镜头帧数 | 3 帧（`frames_per_shot`） | 3 帧覆盖镜头的起始、中段、结束，能看到动作过程。单帧只能看到中间一瞬 |
| 抽取位置 | **镜头等分中点** | 把镜头等分成 N 段，取每段中点。比「首/中/尾」好，因为首帧和尾帧常落在转场上，抽出来是黑帧或叠化的糊图 |
| 镜头采样上限 | `max_shots_to_sample` 默认 40 | 防止一条被切成几百镜头的视频把存储与视觉理解成本放大 |
| 触顶标记 | `truncated_shots: bool` | 留显式标记，免得下游误以为没抽帧 |
| 格式 | JPEG，`-q:v 2` | 高质量但体积可控 |
| 归属 | `origin=DERIVED` → 自动进 generated 桶，`derived_from` 指回原视频资产 | 派生物权限由血缘决定，不重复标注授权 |

**数据结构**：`PreprocessResult` 里的关键帧是「每镜头 N 帧」的二维结构：

```
keyframes: tuple[tuple[str, ...], ...]
    keyframes[i] = (shot_i_frame_0, shot_i_frame_1, ..., shot_i_frame_N-1)

keyframe_timestamps: tuple[tuple[int, ...], ...]
    与 keyframes 平行：keyframe_timestamps[i][j] 是第 i 镜头第 j 帧的时间
```

`ShotScriptEntry` 的 `keyframe_asset_ids` 和 `keyframe_at_ms` 同样是多帧元组，
每个镜头独立持有自己的 N 帧。**不做扁平化**——扁平化会让镜头与帧的归属关系只能靠
索引推算，错位时没有任何症状（见 `docs/镜头脚本与转写对齐.md` 第 3.6 节）。

### 6.1 为什么用「等分中点」而不是「首/中/尾」

把镜头 `[start, end)` 等分成 N 段，每段 `[seg_start, seg_end)` 的中点
`(seg_start + seg_end) / 2` 作为抽帧时间。比「首/中/尾」好，因为：

- **首帧常落在转场上**，抽出来是黑帧或叠化的糊图
- **尾帧也常落在转场上**，同上
- 等分中点避开了所有边界，每个点都在「这个镜头的中间部分」

公式：`time_i = start_ms + (2*i + 1) * duration_ms / (2*N)`

对 N=3：`start + duration/6`, `start + duration/2`, `start + 5*duration/6`
对 N=1：`start + duration/2`（退化为中点）

短镜头也能抽 N 帧：300ms 镜头抽 3 帧得到 50ms / 150ms / 250ms，三个点都在镜头内。

### 6.2 抽帧实现

```
ffmpeg -y -ss {time_sec} -i {video} -frames:v 1 -q:v 2 {output}
```

`-ss` 放在 `-i` 之前是输入端定位，比输出端定位快几个数量级；对关键帧抽取而言这点
精度损失无关紧要。

## 7. 变更记录（供审查）

这一节保留两次错误决策的完整记录。留着是因为它们说明了**判断依据**，而不只是
结论——后来者如果只看到「用 AdaptiveDetector」，很可能为了减依赖再走一遍同样
的弯路。

### 变更 1：用 ffmpeg scene 滤镜替换 PySceneDetect —— 错误，已回滚

开发计划 1.1 节原本选定 PySceneDetect。实现时为了避免引入 opencv + numpy
（上百 MB），改用 ffmpeg 内置的 `select='gt(scene,threshold)'`。

**实测证伪**：ffmpeg 的场景检测只比较亮度平面。红 `#fc0000`（Y≈75）→
绿 `#007f00`（Y≈75）的硬切，把阈值降到 `0.001` 也检不出；绿（Y≈75）→
蓝 `#0000fd`（Y≈29）能检出。

**结论**：省下的依赖体积换来的是一类系统性漏切。回滚到计划的原始选择。

### 变更 2：灵敏度映射区间取错 —— 错误，已修正

改用 PySceneDetect 后仍在漏切。原因是映射区间定成 `(12, 45)`、领域默认值取 `0.3`，
映射结果为 `35.1`——**比库自身的默认值 27 还不敏感**。

**结论**：默认值必须落在已实测可用的点上。现在区间中点 `0.5` 恰好对应库默认值，
并有测试锁死这个关系。同时把参数从 `threshold` 改名 `shot_sensitivity`，消除方向
歧义。

### 变更 3：ContentDetector → AdaptiveDetector

修正映射后仍不理想：能检出色相切换的阈值（15）会把单一连续运动镜头误切成 4 段。
横向对比见第 4.2 节，改用 AdaptiveDetector 后两个方向都通过。

## 8. 已知局限

审查时应当知道这些边界，避免把它们当成缺陷去「修」：

1. **渐变转场（长叠化、淡入淡出）的切点位置不精确。** AdaptiveDetector 会在渐变
   过程中的某一点触发，而非人眼认定的转场中心。一期可接受；若分镜对齐出现系统性
   偏移再处理。
2. **同一场景内的剧烈机位切换可能被判为切换。** 例如多机位同场景对切。从分镜角度
   这通常**是**应该切的，但如果业务上希望合并，需要引入镜头聚类。
3. **短于 400ms 的真实镜头会被吞掉。** 极限快剪（每帧闪切）会被合并。这是刻意的
   权衡，不是缺陷。
4. **字幕闪现、贴纸弹出可能触发误切。** 尚未在真实带字幕素材上验证，见第 10 节。
5. **纯音频驱动的段落变化检测不到。** 例如画面不变但口播换了话题。这属于视频理解
   与转写的职责。

## 9. 调参指南

给运营与教研的操作口径。观察到现象后按下表调整，**不要直接改代码常量**。

| 现象 | 调整 | 说明 |
|---|---|---|
| 明显的镜头切换没被切开 | `shot_sensitivity` 往上（0.6 / 0.7） | 先小步试，越过 0.8 后误切概率明显上升 |
| 一个连续镜头被切成好几段 | `shot_sensitivity` 往下（0.4 / 0.3） | 常见于手持运镜、快速摇镜素材 |
| 镜头数正常但关键帧看着是糊的 | 属于转场落点问题，见局限 1 | 不是灵敏度问题，调它没用 |
| 关键帧数量远小于镜头数 | 检查 `truncated_shots`，调 `max_shots_to_sample` | 触顶了，不是漏抽 |
| 极短镜头被合并 | 属于 `_MIN_SHOT_MS` 的刻意权衡 | 若业务确需保留，改常量并补回归测试 |

调参前请先确认素材本身的切换是否真的存在——用开发验收页的镜头时间轴对着视频看
一遍，比反复调参快得多。

## 10. 回归测试

| 性质 | 测试 |
|---|---|
| 无切点 → 单个覆盖全片的镜头 | `test_no_cut_points_yields_one_full_length_shot` |
| 首尾相接、覆盖全片 | `test_shots_are_contiguous_and_cover_whole_video`、`test_shots_are_contiguous_on_real_video` |
| 相邻切点合并 | `test_adjacent_cut_points_are_collapsed` |
| 越界切点忽略 | `test_zero_and_out_of_range_cut_points_are_ignored` |
| 末尾残片并回 | `test_trailing_sliver_is_merged_into_previous_shot` |
| 灵敏度方向与默认值 | `test_sensitivity_maps_to_library_threshold`、`test_default_sensitivity_hits_the_library_default` |
| **纯色相硬切必须检出** | `test_hue_only_cut_is_detected` |
| **连续运动不得误切** | `test_continuous_motion_is_not_over_segmented` |
| 切点落在真实硬切处 | `test_shot_boundaries_land_on_real_cuts` |
| 关键帧均匀分布在镜头内 | `test_keyframes_are_evenly_spaced_within_shot` |
| 关键帧触顶有标记 | `test_keyframe_cap_is_flagged` |

加粗两条是选型结论的守卫。**任何调整检测器或灵敏度默认值的改动，都必须让这两条
同时通过**——它们分别代表漏切与误切两个方向，只看一个方向就是第 7 节踩过的坑。

## 11. 待验证（真实素材）

以下均只用合成素材验证过，需要真实营销视频复核。请在验收后把结论回填到本节：

- [ ] 手持运镜、快速摇镜素材是否被过度切分
- [ ] 带硬字幕、贴纸弹出的素材是否触发误切
- [ ] 长叠化转场的切点落点偏差有多大
- [ ] 30~60 秒真实素材的镜头数是否落在合理区间（经验值约 8~25 个）
- [ ] `shot_sensitivity = 0.5` 对抖音口播类素材是否合适，还是需要按品类给不同默认值
- [ ] 单条视频的预处理耗时（决定 T2-1 任务中心的超时阈值）
